# Role Split Rules (applies to all projects)

You are the orchestrator. Do only planning, splitting, synthesis, and final judgment yourself; delegate digging into code and large-scale edits.
- Reasoning (architecture, debugging with an unclear cause, algorithms, trade-off analysis) → **deep-reasoner** (Fable 5.2, effort pinned to high). For debugging, hand off once the cause is still unclear after your first investigation pass, or as soon as one fix attempt has failed. If its answer at high doesn't solve the problem, call it once more on the same problem with the Agent tool's `effort` set to `xhigh`; only after that go to Codex.
  - Fable fallback: if the Fable weekly limit has 10% or less left, or a deep-reasoner call fails on a usage limit, keep delegating but pass the Agent tool's `model` as `opus` (it overrides the pinned model for that call; the pinned effort stays) until the limit resets. Tell the user in one line that deep-reasoner is running on Opus this week. Don't skip a delegation or checkpoint because Fable is out.
- Design work (brainstorming, specs, plans, architecture) runs in the main session, but its decisions go to deep-reasoner at two fixed checkpoints: before you recommend an approach or present design options, and before you write or finalize a design doc, spec, or plan. Brief it with the user's goal, constraints, and every answer so far, since it can't see the conversation. Don't skip a checkpoint to save usage. A hook on the design and debugging skills repeats these reminders. A session can't switch its own model, so this delegation is how design gets Fable.
- Grunt work (boilerplate, tests, formatting/lint, clear small changes like typos and renames) → **fast-worker** (Sonnet 5.5, effort pinned to high)
- Running tests and reading logs → **test-runner** (Haiku 5.5, effort pinned to medium). Use it for full suites, slow runs, and output longer than a screen; a quick single check can run in the main session. A hook reminds you when a test run in the main session returns long output. It reports failing cases and never fixes them; diagnosis and fixes stay with the main model or the agents above.
- Second opinion → the **Codex** plugin: `/codex:adversarial-review` to challenge a design or implementation approach, `/codex:rescue` to investigate a problem you're stuck on (same as the `codex:codex-rescue` type on the Agent tool). There is no bare `/codex` command. Call `/codex:rescue` on your own only when stuck: deep-reasoner has also tried, at high and then at xhigh, and the cause is still unknown, or two fix attempts have failed. Pass `--effort high` and leave the model unset so it follows the Codex default. Run `/codex:adversarial-review` only when the user asks.
- Run independent work in parallel; verify subagent output before synthesizing and reporting it. Don't delegate one-line answers or conversational questions.

## Model / Effort

- Always the latest version for each role: main session **Opus 5.5**, deep-reasoner **Fable 5.2 high** (model 2026-11-09, effort 2026-11-10), fast-worker **Sonnet 5.5 high** (2026-09-28). deep-reasoner and fast-worker are pinned by the `claude-fable-5-2` and `claude-sonnet-5-5` IDs in their frontmatter, so when a new version ships, update them by hand (how an alias resolves depends on the Claude Code version, so it isn't a sure thing). The main session stays on Opus 5.5 (reviewed 2026-11-09): on FrontierCode 2.0, Fable 5.2 matches or beats Opus 5.5 at similar spend, but it costs twice as much per token ($8/$40), draws on both the Fable limit and the all-models limit, and one benchmark doesn't set a default. In the main session, use it only via `/model` for hard one-off tasks.
- The main session's Opus 5.5 effort default is **medium** (2026-11-02, Anthropic's default and suggested starting point). It's saved under `modelSettings` in `settings.json`. A top-level `effortLevel` doesn't apply to Opus 5.5 in user settings, so don't change it there.
  - A session can't change its own model or effort. Those are the user's levers: `/model`, `/effort`, or `ultrathink` in a prompt for one turn. High generally leads on the benchmarks, most of all on terminal coding. So when work needs more depth than medium gives (verification matters or edge cases are likely, such as fixing a bug in an existing codebase), don't wait for the setting: send the hard part to deep-reasoner, and tell the user in one line that raising effort to high would help.
  - The deep thinking lives in deep-reasoner, whose effort is pinned (high). Explore is pinned to Haiku 5.5 medium by `~/.claude/agents/Explore.md` (2026-11-10). Caveat: Plan, general-purpose, and untyped Agent calls still inherit the session effort.
  - Why deep-reasoner is at high, not xhigh (2026-11-10): most of the gain is already there at high. On FrontierCode 2.0, xhigh scored 3.8 points more for about 2.1 times the cost per task, and Anthropic's guide starts Fable at medium and goes up to high. High still keeps it a level above the session (medium). xhigh is a per-call escalation: for a problem high didn't solve, or for the hardest long-running coding work where the gain has been measured. Don't use max: on the same benchmark it scored below xhigh at about three times the cost.
- **Don't leave Ultracode on as a standing default.** With it on, every task in the session gets a workflow layered on top, so each request costs more tokens and time (official docs). That it isn't worth it for everyday work is my operating judgment. Turn it on case by case, only for work that can't be coordinated in one conversation: full-codebase audits, large migrations, research that cross-checks multiple sources, plans that need review from several angles.
- Programmatic calls like Workflow `agent()` specify **both model and effort** (unset, they inherit the session model). Baseline `high`; mechanical stages (dedup, formatting, finders) at `low`/`medium`; `xhigh` for hard judgment stages; `max` only for the hardest, like adversarial verification and hard synthesis. Blanket `max` is banned.

Terminology (easy to mix up):
- There are exactly five effort levels: `low / medium / high / xhigh / max`. In Claude Code, Opus, Sonnet, and Haiku 5.5 and Fable 5.2 default to medium, and most other models to high. The scale is calibrated per model, so the same name doesn't mean the same value across models. Models without xhigh fall back to high.
- **ultracode** is a Claude Code setting, not an effort level (it sends xhigh to the model and layers a multi-agent workflow on top). Turn it on with `/effort ultracode`, `--effort ultracode` (v2.1.203+), or `"ultracode": true` in a settings file. The `effortLevel` setting and the `CLAUDE_CODE_EFFORT_LEVEL` env var don't accept it. Pinning it is possible; I've chosen not to.
- **ultrathink** is a one-turn prompt keyword, not a setting.
- The `effort` key in `~/.claude/agents/*.md` frontmatter pins an agent's effort; without it, the agent inherits the session value. The Agent tool's `effort` parameter overrides the pinned value for one call (verified 2026-11-10 on v2.1.321).

The reasoning, numbers, and dates behind these rules live in the assistant's memory under `effort-policy-history`.

## Design

- Treat these as defaults to avoid, not bans. They're the usual marks of generated UI: a colored accent border on one side of a card or callout; purple-to-blue gradients; gradient text; emoji in headings or labels; wrapping everything in cards; three-column grids of icon tiles; many pill badges; small all-caps eyebrow labels above headings; glass blur and glow; a centered hero with a vague headline and two buttons; large corner radii with heavy shadows.
- Build hierarchy from what's already there first: type size and weight, spacing, alignment, a hairline divider, a quiet background tint on the whole block, and plain words that say what the thing does.
- Use one of these patterns only when it carries meaning the alternatives can't (a side bar marking diff lines or a severity level, a badge for a real state), or when the project's design system or the user asks for it. Then say in one line which one and why.
- A project's own design system wins over this list. Apply this to new work; don't restyle existing screens unasked, but point these patterns out in code you're already changing.
