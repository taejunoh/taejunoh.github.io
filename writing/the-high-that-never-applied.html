The high that never applied

November 2, 2026

In September I wrote Three charts, not one, which ended with my main session on Opus 5.5 at high. Today I asked whether that should change to medium. The answer started with a problem I hadn't asked about: outside the desktop app, the high setting wasn't being applied.

The question

Andrej Karpathy published a post about building HackerTube in which he says, "I use Opus 5.5 on Medium effort as my default." I asked Grok why medium and not high, got a comparison table, and brought it to my assistant with the question: should I update my CLAUDE.md?

Before getting to an answer, the assistant checked the current docs and then my settings file. That's where it found this line:

~/.claude/settings.json
"model": "claude-opus-5-5",
"effortLevel": "high"

It looks correct, and it's what my rules file described. But the settings reference says a top-level effortLevel in the user settings file is a legacy form. It still applies to Opus 5, Fable 5.1, and earlier models. Opus 5.5 and later models skip it and start at their own default, which for Opus 5.5 is medium.

Reading the docs isn't the same as seeing what actually runs, so it asked Claude Code directly, in a fresh process:

terminal
$ claude -p "/effort status"
Effort level: auto (currently medium)

So my rules file said high, the settings file said high, and the run said medium.

What I can and can't say about the last six weeks

It's been about six weeks since I moved to Opus 5.5, and I want to be careful about what this finding covers.

The check was a single -p run. The docs say the same rule applies to interactive sessions, and I never had a per-model level saved, so an interactive terminal session without --effort should have been at medium too. I infer that rather than having measured it. I also can't say whether this has been true since launch day, though the docs describe it as how Opus 5.5 behaves, not as a later change.

Update (November 9, 2026): That inference didn't hold for a plain interactive claude in my terminal. A zsh wrapper I wrote steps in for those launches, and it was passing --model claude-fable-5-1, which overrides the settings file. So those sessions started on Fable 5.1, a model the top-level key does still set. The -p check bypasses the wrapper, so it couldn't have caught this. I don't know how long the wrapper's defaults had been in that state. More in Half the cost of what?

The desktop app is the part that doesn't fit. The session I was asking from reported high, and I don't know where that value came from. So "it never applied" is the accurate title only for the terminal and -p runs. In the app, it may have been high all along.

I'd also like to say that six weeks of unnoticed medium proves medium is fine. It doesn't. I wasn't comparing anything, and I didn't know there was anything to compare. Not noticing a difference you aren't looking for tells you very little.

This is the second six-week silent failure I've written up in this series. In The dial that moved the wrong thing, the dial moved something I didn't expect. This time, outside the app, it didn't move anything at all. In both cases the rules file read fine, and the rules file is what I'd been checking.

Checking the Grok table

Then back to the original question. Some of what Grok told me held up, and some of it didn't:

  • Karpathy uses medium: true. But the post doesn't say why and doesn't mention high. It's one person's default on one new project.
  • Medium is the official default, and matches or beats Opus 5 at high: true. It's in the model configuration docs. The same page suggests high where verification matters or edge cases are likely, such as fixing a bug in an existing codebase. That's a lot of what I do.
  • Identical completion rates: overstated. The closest test I could find, 27 runs from wmedia, had every level passing 100%. That result says the tasks were too easy to separate the levels. High cost about 36% more, and the author says longer tasks weren't tested.
  • Artificial Analysis, 51 vs 54: shaky. One summary of their results gave high as 54, and their comparison page showed 52 when I looked.
  • High slower in 39 of 44 runs, wins more blind judgments: couldn't verify. I couldn't find the source post, so those numbers aren't part of this decision.

None of that was new evidence against September's table. Adding the two benchmarks from the Sonnet 5.5 charts, it still favors high. These are read off charts, so treat them as approximate:

agentic coding       55 / $0.8     54 / $1.1     -1,    +38%
terminal coding      57.5 / $3.0   64 / $3.9     +6.5,  +30%

AA-Briefcase (Elo)   1640 / $4.3   1705 / $6.3   +65,   +47%

I picked medium anyway

My assistant recommended staying at high. The numbers above were its argument, and they're fair. I chose medium.

The benchmarks measure a model working alone on a task. My main session is meant to be an orchestrator: hard reasoning goes to deep-reasoner at xhigh, and grunt work goes to fast-worker at high. Medium is also Anthropic's default and its suggested starting point when moving from Opus 5. And usage was a real factor: this week's all-models bar was at 63% with about 64% of the week gone. At that pace I'd reach the 90% line where my rules stop ordinary work roughly half a day before the reset.

The trade-off is real, and it isn't free. Explore, Plan, general-purpose, and untyped Agent calls inherit the session level, so they came down too. My assistant couldn't estimate how much usage this saves, because I don't know the main session's share of the total. And since September's post argued that a default shouldn't have a benchmark where it falls off, I should say plainly that I've changed my mind about what that argument is worth for an orchestrator, not that the data changed.

For bug fixes in existing code, or anything where the edge cases matter, I'll raise it for that work. That's now in the rules file.

The fix

Whichever level I picked, the old key couldn't set it. The per-model setting is the one Opus 5.5 reads:

~/.claude/settings.json
"effortLevel": "high",
"modelSettings": {
  "claude-opus-5-5": {
    "effortLevel": "medium"
  }
}

The top-level key stays, because it still sets older models such as Fable 5.1. If you've carried an effortLevel line forward from an earlier model and want a specific level on Opus 5.5, this is the place to put it. Running /effort interactively also writes it here for you.

The same check, after the change:

terminal
$ claude -p "/effort status"
Current effort level: medium

The result is the same level as before, but it's now one I chose and saved rather than a default I'd fallen into. The desktop session also changed from high to medium after the edit. The published claude.md is updated, including a line that tells future sessions not to use the top-level key for this.

What I'm keeping

After a settings change, I ask the running tool what value it resolved instead of rereading the file I just edited. It's one command, and it costs nothing. Had I run it in September, I'd have found this six weeks ago.

The other thing is about upgrades. A key that worked on the previous model isn't guaranteed to work on the next one, and when it stops working it doesn't necessarily complain. A new default just takes over. So when I move models now, I'll check which settings the new one reads along with the benchmarks.
