Defaults to avoid

November 12, 2026

One of my apps has a screen that lists the week's workouts: upper body A, lower body A, upper body B, lower body B, each with its exercises underneath. Down the left side of the list runs a thin green bar. Nobody asked for it. It doesn't mean anything. It's there because that is what generated UI tends to do when it wants something to look organized.

Once I noticed it, I saw it everywhere. So I asked my assistant two things: can I stop this from happening unless it's really needed, and where does a rule like that belong?

Where it goes

There were four places it could live. A project's own rules file covers one app. A skill loads only when the work looks like UI, which keeps it out of every other session but means it may not load when it should. A hook could scan edited files, and for web CSS a line like border-left: 3px solid is easy to catch. In SwiftUI there are too many ways to draw the same bar for a pattern to find them all.

The rule is a few lines and applies to every project, web and iOS alike, so it went into my global CLAUDE.md, which every session reads.

Each pair shows the same content. The left side adds the decoration; the right side uses size, weight, spacing, or a hairline instead.

What they share is that none of them comes from the content. Each is decoration added out of habit. The alternatives mostly use what's already on the page: type size and weight, spacing, a hairline divider, and words that say what the thing does. On the workout screen, a heavier title and a little more space between the four days separate them better than the bar did.

Not a ban

Before anything was written, I asked how it would be phrased, because "never" felt wrong. A side bar is exactly right for marking added and removed lines in a diff, or the severity of an alert. A badge is right when it shows a real state. A rule that says "never" would block those along with the habits.

So the rule says "defaults to avoid." Use one only when it carries meaning the alternatives can't, or when the project's design system or I ask for it, and then say which one and why in a single line. That last part matters most. A pattern that has to be justified out loud stops showing up by accident.

~/.claude/CLAUDE.md
## Design

- Treat these as defaults to avoid, not bans. They're the usual marks of generated UI: a colored accent border on one side of a card or callout; purple-to-blue gradients; gradient text; emoji in headings or labels; wrapping everything in cards; three-column grids of icon tiles; many pill badges; small all-caps eyebrow labels above headings; glass blur and glow; a centered hero with a vague headline and two buttons; large corner radii with heavy shadows.
- Build hierarchy from what's already there first: type size and weight, spacing, alignment, a hairline divider, a quiet background tint on the whole block, and plain words that say what the thing does.
- Use one of these patterns only when it carries meaning the alternatives can't (a side bar marking diff lines or a severity level, a badge for a real state), or when the project's design system or the user asks for it. Then say in one line which one and why.
- A project's own design system wins over this list. Apply this to new work; don't restyle existing screens unasked, but point these patterns out in code you're already changing.

The last line keeps it from turning into a rewrite of everything I've already built. It applies to new work, and existing screens get flagged, not restyled.

My own site

It seemed fair to check this site against the list. It has no side bars, no purple gradients and no emoji headings. It does have three of the others: the small all-caps role line on the home page, rounded status chips on the project cards, and cards with a soft shadow.

I'm keeping them for now, and the rule says why that's allowed. This site has its own look, a notebook on graph paper with taped-on cards, and those three pieces belong to it. Some of the chips show a real status, such as "In development" or "Retired Sep 2026", which is the kind of meaning the rule makes room for. Others only name the platform, like iOS or Python, and those are closer to the habit. If I redesign the site, they'll all have to earn their place again.

What I'm keeping

The useful question about a design pattern isn't whether it's allowed. It's whether the thing on the screen would lose anything without it. The green bar on my workout screen wouldn't. That's the test I want applied before the pattern is drawn, not after I notice it.

I haven't seen this rule work on a real screen yet. It reaches new UI work from the next session on, and the first one will tell me whether "say which one and why" actually stops the habit.
