The playbook I hadn't read

November 10, 2026

Yesterday I moved deep-reasoner to Fable 5.2. The same day, Anthropic published Addy Osmani's guide to choosing a Claude model. This morning I asked my assistant a simple question: did you use this when you updated my CLAUDE.md?

No

It didn't guess. It searched my Claude config folder for the URL and found it only in the conversation we were having. Then it read the memory file where I keep the reasons behind each rule. The sources listed there were benchmark charts, a launch thread, a news write-up, a leaderboard and a system card. The guide wasn't one of them. So I asked it to read the guide and compare.

Where we agree

Most of the file held up. The guide says to start most work on Opus 5.5 at medium, which is my main session. It says to move to high for debugging, which my rules already say for bug fixes. It saves Fable 5.2 for the hardest work, for when Opus 5.5 at high still falls short. That's what deep-reasoner is for. It also says to test Fable 5.2 before raising Opus past high on a hard task, and that's the trade I made yesterday. And it ends by telling you to measure on your own tasks, which is close to my rule that one benchmark doesn't set a default.

Where I sit higher

The guide starts Fable 5.2 at medium and moves to high from there. It warns that past high, one more effort level can cost as much as a bigger model. deep-reasoner runs at xhigh. My own numbers show what the guide is warning about:

Fable 5.2 · FrontierCode 2.0 · score / cost per task
high     45.3 / $6.72-8.40
xhigh    49.1 / $14.19-17.73

3.8 more points for about 2.1 times the cost per task. I'm keeping xhigh for now, on purpose: the seat is rarely called and only gets the hardest problems, and it stays a level above the main session. But I'm further outside the guide's advice than I'd realized. That makes the rule for when to step down to high matter more.

fast-worker, my Sonnet 5.5 seat for mechanical work, is one level higher too. The guide starts Sonnet at medium for well-scoped work, and I run high. My notes from September have the reason: on Anthropic's own charts, medium to high was the biggest jump at almost no added cost. That's a difference I chose, so it stays.

The note that went stale

This was the useful part. In October, when Haiku 5.5 came out, I wrote down that my Claude Code build still resolved the haiku alias to Haiku 4.5. I'd wait for an update before using it. The guide says the alias resolves to Haiku 5.5 from v2.1.293. I'm on 2.1.321, which I installed yesterday for Fable 5.2. So the wait had been over for a while, and nothing in my setup was going to tell me. A note that says "waiting for X" has no way to notice when X happens.

The guide also says the built-in Explore subagent, the read-only one that searches a codebase, runs on the session's model. It suggests defining your own Explore pinned to Haiku. I had nothing like that. A hook makes my orchestrator name a model whenever it calls Explore, so the choice was being made fresh on every call.

What changed

I added one file. An agent with the same name as a built-in one replaces it:

~/.claude/agents/Explore.md
---
name: Explore
description: Read-only search agent for broad fan-out searches ...
tools: Read, Bash
model: claude-haiku-5-5
effort: medium
---

The model is pinned by ID, not alias, like my other two agents. Medium is Haiku 5.5's default.

Then I checked it the way I check every agent change: from a new claude -p process, because agent definitions load when a session starts. Called with no model set, Explore answered from claude-haiku-5-5.

The check caught one mistake. My first version listed Grep and Glob as tools, copied from how Explore usually describes itself. The agent reported having only Read and Bash, so I removed the two that don't exist. Two limits I should be plain about. I can't confirm from the output that medium effort was applied. And "read-only" is only an instruction in the prompt, because Bash can still write files.

The published claude.md now says Explore is pinned, and that only Plan, general-purpose and untyped Agent calls still inherit the session's effort.

What I left out

The guide suggests an order for when a model falls short. First check that it can verify its own work. Then raise effort one level. Only then move up a model. If outcomes can be checked automatically, run everything at low and re-run only the failures at high. In its SWE-bench Pro example, that passed about 97% of tasks for $0.17 each, against 95.3% for $0.29 with everything at high. I like it, but my rules don't have a place where tasks are retried in bulk, so I didn't add it yet.

What I'm keeping

I've been setting these rules from benchmark curves and launch posts. A guide written for exactly the choice I'm making is a different kind of source, and I'd skipped it. Next time a model ships, I'll read the vendor's own guidance alongside the numbers.

The other one is about my notes. Any note that says "waiting for" should also say what to check, so that a later session can run the check instead of trusting the note. This one had the check written down, and nobody ran it until an outside source made me look.
